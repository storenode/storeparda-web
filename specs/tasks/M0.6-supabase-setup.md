# M0.6 — Supabase client setup

**Status:** Completed
**Version:** 1.0.0
**Est:** 2 hrs
**Tracking:** [Issue #26](https://github.com/storenode/storeparda-web/issues/26)

## What this is

StoreParda's backend is Supabase (Postgres + Auth + Storage), per the project
constitution (`specs/constitution.md`, §4). Before this task, `@supabase/supabase-js`
was installed as a dependency (from M0) but nothing in the app actually used it — there
was no configured client, and no tooling to manage the database schema.

This task wires up the **connection only**: a Supabase project to develop against, the
environment variables the app needs to reach it, a single shared client the rest of the
app can import, and the CLI needed later for schema migrations. It does not create any
database tables, authentication flow, or row-level security policies — that's module
M1 (Constitution §5), which builds on top of this.

## Scope

**Included:**
- Supabase CLI installed as a dev dependency (`supabase`), for future schema
  migrations and type generation against the project — this does **not** run a local
  Docker Supabase stack; see "Remote-only, by design" below
- A single shared Supabase client (`src/lib/supabaseClient.ts`) that reads the project
  URL and anon key from environment variables and throws a clear error if either is
  missing, instead of failing silently or crashing somewhere unrelated later
- `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` typed in `src/vite-env.d.ts` so
  autocomplete and type-checking work on `import.meta.env`
- Verified the configured project is actually reachable (a live connectivity check,
  not just "the file has values in it")

**Explicitly not included (deferred to M1):**
- Any database tables, migrations, or schema at all
- Row-level security (store-level data isolation)
- Authentication (phone OTP or Google Sign-In) — the client here is unauthenticated;
  no sign-in flow uses it yet
- Any UI that reads or writes Supabase data

## Remote-only, by design

Per the founder's instruction, local development connects directly to a **remote**
Supabase project rather than running Supabase's local Docker stack (`supabase start`).
That means:
- The Supabase CLI is used for project-level commands (`supabase link`, migrations,
  type generation) against the remote project, not for spinning up local Postgres
- Everyone working on this repo needs their own `.env.local` pointed at that same
  remote project (or their own, if projects diverge later) — there's no "just works
  out of the box" local database

## Environment variables

`.env.example` (committed, already had these two from M0 — no change needed):
```
VITE_SUPABASE_URL=
VITE_SUPABASE_ANON_KEY=
```

`.env.local` (git-ignored, never committed): filled in with the actual project URL and
anon key from Supabase → Project Settings → API. Only the **anon** key ever goes here —
it's public by design (compiled into the client bundle). The service-role key must
never appear in this repo; it belongs in Supabase Edge Function secrets only
(Constitution, M0 setup guide §11).
